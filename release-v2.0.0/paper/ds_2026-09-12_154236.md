# 对抗性审稿意见：ACSD — An Executable Profile for Anonymous Scholarly Releases

> 审稿人：ds（deepseek-v4-pro）
> 审稿时间：2026-09-12 15:42
> 对象：`paper/acsd-v2.tex`（release-v2.0.0）

**总体判断：Major Revision（大修）。** 核心密码学设计没有发现根本性错误，论文最可贵的品质是诚实克制地反复声明 non-claims；但评估部分不可复现、存在一处可验证的跨实现 canonicalization 回归、文献引用有一处年份错误、新意定位不够锐利。下面按正确性 → 文献真实性 → 行文 → 新意展开，每条附核验证据。

---

## 一、正确性（技术正确性）

### 1.1 【严重】表 2 的评估数字无法从本论文随附的 release 复现

论文表 2（"Current executable evaluation corpus"）列出的数字：

- Standalone release versions 8/8
- Author endorsements 18/18
- Signed series objects 7
- Closed scenarios 13/13
- Independent profile checks 30/30
- Canonical JSON regression 11/11
- Public-manifest entries 111/111

这些数字**逐字对应** v1 代码库 `release-staging/acsd-anonymous-series-v1.0.0/public/artifact/EXAMPLE-OUTPUT.md` 的内容：

```
standalone_releases: 8
author_endorsements: 18
series_signed_objects: 7
scenarios: 13
profile checks: 30 passed, 0 failed
public artifact manifest: 111 passed, 0 failed
```

我在 v1 代码库逐项核验，全部对得上：`artifacts/releases/` 有 8 个 release JSON、`artifacts/endorsements/` 有 18 个 `.scitt`、`artifacts/series/` 有 7 个 JSON 对象、`scenarios.json` 有 13 个场景、`canonical-json-corpus.json` 有 11 个 case。

**但 v2 release（本论文随附的 `release-v2.0.0` 目录）里一个这些 fixture 都没有。** 它实际可复现的只有：16 个测试方法（其中 3 个默认 skip，见 1.4）、`demo/MANIFEST.sha256` 的 2 个条目、以及 4 个 Lean 定理。表 2 把 v1 的成果和 v2 的"4 PEC theorems"混在一张表里，标题还叫"Current executable evaluation corpus"，读者无法从论文随附目录复现表 2 的绝大多数数字。**必须拆分标注：哪些是继承自 v1 的结果，哪些是 v2 新增的、给出复现命令的结果。**

### 1.2 【严重】canonical JSON 存在 v1→v2 的 Unicode 转义回归

这是最需要确认的一点，因为它是一个**可验证的、真实存在的跨实现不一致**：

- v1 Python（`generate.py:67`）：`json.dumps(value, ensure_ascii=False, ...)`
- v1 Node（`verify-standalone.cjs:30`）：`JSON.stringify(value)`（默认不转义非 ASCII）
- **v2 Python（`pec_core.py:29`）：`json.dumps(obj, ensure_ascii=True, ...)`**

v1 的 Python 和 Node 在非 ASCII 字符串值上是**一致**的（都保留原始 UTF-8 字节），所以 v1 声称的"11/11 Python–Node agreement"成立。但 v2 的 `pec_core.py` 把 `ensure_ascii` 改成了 `True`，于是对含非 ASCII 字符串值的对象（比如 `{"label":"匿名"}`）：

- v2 Python 产出 `{"label":"\u533f\u540d"}`（转义）
- Node 产出 `{"label":"匿名"}`（6 字节 UTF-8）

两者字节不同 → 摘要不同 → 签名/绑定验证直接失败。`SPEC.md` 第 46 行只规定"recursive ASCII-key sorting"，**没有规定字符串值的 Unicode 转义行为**，这是规范空白；而 v2 的实现改动恰恰落在这个空白里，制造了与 v1 Node verifier 的回归。目前 demo 全 ASCII（`"urn:uuid:demo"`、`"a"*64`），所以测试没暴露它。

### 1.3 【中等】demo 占位符与论文正文直接矛盾

论文 133 行写："the released fixture contains complete UUIDs and exact digests"。但实际 `demo/pec.json` 里是：

```json
"work_id": "urn:uuid:demo",
"release_digest": "aaaaaaaa...a",     // 64 个 'a'
"manuscript_sha256": "bbbbbb...b",     // 64 个 'b'
"statement_digest": "cccccc...c"       // 64 个 'c'
```

`work_id` 不是有效 UUID，三个 digest 全是占位符。也就是说 v2 demo **从未绑定任何真实内容字节**——摘要里"a release binds exact content bytes"这一核心主张，在 demo 里没有被演示。要么用真实 release 字节替换，要么明确标注 demo 只是语法自洽演示。

### 1.4 【中等】"16 passing tests" 不准确

`STATUS.md` 和 `README.md` 都说 "16 passing tests"。但 16 个测试方法里有 3 个带 `@unittest.skipUnless(...)`（`test_v1_adapter`、`test_package_adapter`、`test_node_integration`），默认 `ACSD_V1_ROOT` 指向的目录不含 v1 fixture，因此**默认实际是 13 passed + 3 skipped**，不是 16 passed。unittest 的 skip 不计入 "passed"。

### 1.5 【中等】Node.js 验证路径不在 release 包内

摘要声称 "independent Python and Node.js verification paths"。但 v2 release 目录里没有任何 `.js`/`.cjs` 文件——`verify-standalone.cjs` 在 v1 代码库（`release-staging/.../public/artifact/`）里，`pec_core.py:verify_v1_package_with_node` 通过 `subprocess` 调 `node` 委托验证，且 `test_node_integration.py` 默认 skip。要跑通这条"独立验证路径"，需要外部 v1 工作区 + 手动设置 `ACSD_V1_ROOT`。这削弱了"独立跨实现验证"的可复现性。

### 1.6 【观察】Lean 模型实质内容极薄

`formal/ACSD/PEC.lean` 里 4 个定理是 `Accepted` 定义的**直接字段投影**：

```lean
theorem accepted_implies_all_required_keys_approved {p} (h : Accepted p) : AllApproved p := h.1
```

`Accepted` 被定义为 `AllApproved ∧ eventSequenceValid ∧ forbidsSocialClaims`，所以这些定理是定义展开级别的重述。axiom-free 确实成立（`lake-manifest.json` 无 Mathlib，`Digest` 只是一个 `Nat`），但代价是模型**什么都没编码**——哈希、签名、解析、事件链的真实结构全是 `Prop` 假设。论文 215-216 行诚实承认了范围（这点值得肯定），但贡献第 5 条"axiom-free Lean model of selected acceptance conditions"的措辞与其实质内容不成比例。

## 二、文献真实性

逐个抓取 RFC 官方元数据（rfc-editor.org）核验：

- **RFC 9052（COSE）**：标题、作者 J. Schaad、2022 年，全部正确。✓
- **RFC 3161（TSP）**：标题、C. Adams et al.、2001 年，正确。✓
- **RFC 9943（SCITT）**：标题 "An Architecture for Trustworthy and Transparent Digital Supply Chains" 正确，作者 H. Birkholz et al. 正确，**但年份错误**——论文写 2024，RFC 编辑器的权威元数据显示 `pub_date = "June 2026"`。RFC 9943 直到 2026 年 6 月才发布。应改为 2026，或者如果要引 2024 年的形态，应标注 `draft-ietf-scitt-architecture-XX`。
- **PROV-DM**（W3C 2013）、**SWHID v1.2**、**Trusty URIs**（Kuhn & Dumontier, ESWC 2015, arXiv:1401.5775）、**OpenTimestamps**：均真实。

结论：文献真实性整体良好，唯一硬伤是 RFC 9943 的年份。

## 三、行文

**优点（值得先说）：** 全文克制、诚实，反复划定"证明什么 / 不证明什么"的边界（摘要、威胁模型、Time Evidence、Limitations 各节都一致贯彻）。这在"匿名签名论文"这类极易过度声称的领域里是难得的，应该保持。

**问题：**

1. **表 2 有误导性**：标题"Current executable evaluation corpus"未说明数字来自 v1 代码库、本 release 无法复现（见 1.1）。
2. **摘要与实现的措辞落差**："independent Python and Node.js verification paths""axiom-free Lean model"等表述，在实现层面比文字暗示的要单薄（见 1.5、1.6）。
3. **术语精度可提升**：`content-anonymous` vs `author-unlinkable` 的区分在第 71 行才出现，建议在摘要或引言更靠前的位置点明，因为这正是该方法最容易被人误解的地方。
4. 小问题：图 1 用 `verbatim` 画 ASCII 图，`\caption` 里"Cyclic semantic citations"表述可以更精确——是"语义图允许环"，不是"引用本身是循环的"。

## 四、新意

**中等偏弱。** 核心机制——内容寻址（Software Heritage、Trusty URIs）、COSE 签名、RFC 3161 时间戳、匿名密钥——都不是新原语，论文自己也承认"does not claim to replace these systems or invent their primitives"。

真正的增量点有且只有一个相对新颖的构造：**语义引用图（允许环）与密码承诺图（必须无环）的分离 + rank 证书**。这个"两图分离"的表述是论文最有价值的部分，`model-results.json` 也实际验证了 `semantic_reference_graph.has_cycle: true` 而 `cryptographic_dependency_graph.has_cycle: false`。

但问题在于：这个分离与现有内容寻址 + 引用解析工作的**边界不够锐利**。审稿人会问：SCITT（RFC 9943）已经提供"签发声明 + 透明性回执"的架构，PROV-DM 已经提供 provenance 词汇，Software Heritage 已经提供内在标识符——ACSD 在这个特定组合（匿名 + 团队 assent + 循环引用 + 显式非声明）上的**不可替代性**是什么？论文目前没有用足够篇幅回答。作为系统/工程 profile 论文可以接受，但作为研究贡献，新意需要更明确地钉死在一个点上。

---

## 五、建设性意见（按优先级）

1. **修 `ensure_ascii` 回归**：把 `pec_core.py` 的 `canonical()` 改回 `ensure_ascii=False` 与 v1/Node 对齐；同时在 `SPEC.md` 里明确规定字符串值的 Unicode 转义规则（或干脆禁止非 ASCII 字符串值）；并新增一个含非 ASCII 值的 Python–Node 交叉回归 case（现有 11 个 case 里其实有 `utf8-string-value`，但它测的是"输入是否 canonical"，没有测"两个实现产出相同字节"）。
2. **拆分并标注表 2**：明确区分"继承自 v1 的结果（给出 v1 代码库路径与 `EXAMPLE-OUTPUT.md`）"和"v2 新增结果（给出 `python -m unittest`、`python verify_pec.py`、`lake build` 三条复现命令）"。
3. **修文献年份**：RFC 9943 → 2026（或引草案）。
4. **处理 demo 占位符**：要么用真实 release 字节替换 `"a"*64` 等，要么在论文里明说 demo 是语法演示、不含真实内容。
5. **把 Node verifier 纳入 release 包**，或明确声明其为外部依赖并给出获取方式，避免"独立验证路径"名不副实。
6. **Lean 模型二选一**：要么真正建模事件链/审批的结构（而非 `Prop` 假设），要么把贡献第 5 条降级为"一个最小抽象模型，仅用于示范非声明策略"。
7. **新意定位**：加一节与 SCITT / PROV / Software Heritage 的逐项对比，明确 ACSD 在"匿名 + 全体作者 assent + 循环引用 + 显式 non-claims"这个组合上的独有价值。

## 一句话总结

方向对、态度诚、设计无明显硬伤，但**评估部分不可复现（v1/v2 数字混淆）、有一个真实的 canonical 跨实现回归、文献有一处年份错误、新意定位偏弱**——修完 1.1、1.2、1.3 和文献年份后，可进入下一轮。
